新機能「$ARGUMENTS」を、このプロジェクトの規約どおりに追加してください。

順番を守ること。**検証の当てを先に決めてから実装する** — 期待値を後付けで
決めると、コードの出力を期待値にしてしまい回帰テストにしかならない。

## 1. 検証の当てを先に決める

実装前に、次を明示して合意を取ってください。

- どの解析解・文献値・別経路の実装と比較するか
- その値の導出 (公式・代入値・数値)
- 妥当な許容誤差とその根拠 (`.claude/rules/validation.md` の表を参照)

比較先が見つからないなら、**極限値** (低周波・高周波・分割数 →∞) や
**既存経路との相互検証** を探すこと。それも無ければ、定量検証できない旨を
先に伝えてから実装に入る。

## 2. 入力キー

`src/input_data.c` に追加。**既定値はキー省略時に従来動作と完全一致**
させる (後方互換)。既存の全検証ケースが 1 つも動かないことを確認する。

## 3. 実装

`.claude/rules/portability.md` と `.claude/rules/physics-invariants.md` に従う。
特に幾何積分やセル構成に触るときは、不変条件の番人になっている判定
(`wire L (ndiv=1)/(ndiv=8)`, `wire Ctotal`, `short dipole R_rad`,
`strip L (surface)`, `plate C (extrapolated)`) を必ず通す。

## 4. 検証ケース

`data/sample/<name>.peec` に**導出をコメントで書き**、
`data/sample/peec_check.sh` に判定を足す。

## 5. ドキュメント

README の理論概要・入力キー表・検証表に追記。制限があれば「制限」節に明記する。
新たに踏んだ移植性の落とし穴は `.claude/rules/portability.md` に追記する。

## 6. 点検

`/preflight` を実行し、全項目 OK を確認してから報告してください。
